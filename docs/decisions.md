## Data model

- **D5 — UUIDv7 ids generated by Postgres 18 `uuidv7()`** as column default. The app may also supply ids
  (needed for offline-created blocks/tasks that are referenced before sync; `uuidv7` npm package).
- **D6 — `version` and `updated_at` maintained by DB triggers** (`drizzle/0001_row_version_triggers.sql`).
  Every UPDATE on `day, plan_option, block, habit, habit_log, task` sets `version = OLD.version + 1`; values the app
  sends are ignored. Optimistic concurrency = `UPDATE … WHERE id = $1 AND version = $expected`; 0 rows → 409.
- **D7 — Times stored as `text` `HH:mm`** with a CHECK regex rather than `time`, so they round-trip exactly as the
  API contract and sort lexicographically. Block times allow 00:00–29:59 (see D54).
- **D8 — `end < start` means the block ends after midnight** (e.g. sleep 23:30→07:00). The block belongs to the
  day it starts. No overnight logic beyond that.
- **D9 — `Day.weeklyGym` and `Day.review` stored as columns** (`weekly_gym_done/target`, `review_energy/mood/text`
  + `reviewed_at`) with CHECKs, not jsonb; the API exposes them as the nested objects from the spec. Makes metrics
  queries trivial.
- **D10 — `block.day_id` is denormalized** next to `option_id`, kept consistent by a composite FK
  `(option_id, day_id) → plan_option(id, day_id)`. Used by `by-external` lookups and metrics.
- **D11 — Calendar events are duplicated per option.** Options A and B each contain their own copy of every
  calendar block; `external_id` is unique per option, not per day.
- **D12 — `day.chosen_option_id` is a plain FK (`ON DELETE SET NULL`)**; "the option belongs to this day" is checked
  in the domain layer. A CHECK forbids `chosen|edited` without a chosen option. A `draft` day that is closed without
  a choice keeps `chosen_option_id = NULL`.
- **D13 — Extra columns not in the spec** (cheap, useful for metrics/audit): `block.status_at`,
  `task.done_at`, `day.closed_at`, `day.reviewed_at`, `proposal.base_day_version`, `proposal.resolved_at`,
  `change_log.forced`.
- **D14 — `PlanOption` carries the mutable columns too** (`version`, `updated_by`…) because the spec says "every
  mutable row".
- **D15 — Postgres enums** (`pgEnum`) for all closed vocabularies. Adding a value later is a one-line migration.
- **D16 — Webhook debounce uses an extra outbox status `collecting`.** User changes for a date are appended to
  the single `collecting` row of that date (partial unique index) and push `next_attempt_at` to now + 120 s;
  `choose` and `proposal.accepted|rejected` set it to now. A worker moves due rows to `pending` and delivers with
  backoff; after 5 failed attempts → `failed`. `webhook_outbox.id` is the `batchId` / `Idempotency-Key`.
- **D17 — Idempotency keys are scoped per actor** (PK `(actor, key)`), store method + path + body hash, and a
  `NULL response_status` means "in flight" (a concurrent duplicate gets `409`). Purged after 48 h by the close-day job.
- **D18 — At most one pending proposal per day**, enforced by a partial unique index; superseding is
  "mark old `superseded`, insert new" in one transaction.
- **D19 — ChangeLog is append-only** with `date` nullable (habits/devices are not day-scoped).

## Auth

- **D20 — Single user row** enforced by a unique, always-true `singleton` column.
- **D21 — WebAuthn user handle** is random bytes in `app_user.webauthn_user_id`. At most one passkey per device.
  Registration/authentication challenges live in a short-lived signed cookie (`SESSION_SECRET`), not in the DB.
- **D22 — Lockout keys.** Per-device counters are keyed by a random **pre-auth device-key cookie** (set on first
  visit), because a browser that never logged in has no `device` row. Global counter key = `"global"`. PIN,
  recovery-code and reset-code failures all count against the same counters. Every check is logged in `auth_attempt`.
- **D23 — PIN reset codes** from `pnpm auth:reset-pin` are stored hashed in `pin_reset_code` (15 min TTL,
  single use). `pnpm auth:recovery-codes` deletes old recovery codes and inserts 10 new ones.
- **D24 — "Locked" device** = `now - last_seen_at > PIN_REAUTH_DAYS`; session invalid when revoked or
  `now - last_seen_at > DEVICE_TRUST_DAYS`. `last_unlock_at` is informational.
- **D25 — 10-min call reminder toggle is per device** (`push_subscription.call_reminders`).
- **D26 — Agent rate limit (120 req/min) is in-memory** — single container, no Redis.

## Resolved at STOP 1 (2026-10-19)

- **D27 — `Day.version` scope (Q1).** Bumped by any write to the day row, its options or its blocks. Tasks and
  habit logs have their own versions and do **not** bump the day.
- **D28 — `PATCH /blocks/by-external/{externalId}` (Q2).** Agenbot never writes to Google Calendar: I edit events by
  hand and Agenbot mirrors what it reads. The mirror goes to **every copy** of the event: all options on a `draft`
  day, and on `chosen|edited` days too (the non-chosen copies are kept consistent for history).
- **D29 — Habit ↔ block link (Q3).** `habit.slug` is the stable key for the agent (e.g. `gym`).
  `habit.block_type` is optional: marking a block of that type `done` upserts the habit log for that date with
  `source` = the actor; undoing removes the log only if that block created it. One log per habit per day, however
  many matching blocks there are. Habits done outside the plan are logged by hand.
- **D30 — `chosen → edited` (Q4).** Triggered by my first schedule-field change (add/move/delete/edit block,
  shift, reorder). Tracking-field changes (done/skipped/outcome/note) keep the day `chosen`.
- **D31 — Calendar events that disappear (Q5).** When an agent replace (or an accepted proposal) no longer contains
  a calendar block: if I already tracked it (status ≠ `pending`, or `outcome`/`note` set), it is **kept** with
  `block.removed_from_calendar_at` set; the UI strikes it through with "Ya no está en Google Calendar" and it still
  counts in metrics. Untouched pending blocks are deleted. If the event comes back (same `externalId`), the
  timestamp is cleared. Migration `0002_block_removed_from_calendar.sql`.

## API contract (STOP 2)

- **D32 — Contract source.** Zod schemas in `src/contract/` + a route catalogue (`src/contract/routes/*`) where every
  route carries paired request/response examples. `pnpm openapi` writes `openapi.yaml` and `docs/api-examples.md`;
  every example is validated against its schema first. CI runs `pnpm openapi:check` (fails on invalid examples or
  stale generated files) and `pnpm openapi:lint` (Redocly). Phase 3 adds contract tests validating real responses.
- **D33 — `orNull(schema)` instead of `.nullable()` on named schemas.** zod-to-openapi 9 drops the `null` branch of a
  `$ref` (`Lead | null` came out as `Lead`); an explicit union emits `anyOf: [$ref, {type: null}]`. Same reason
  for `{...X.shape}` instead of `X.extend()`.
- **D34 — `/api/openapi.json` is compact by default** (no examples, ~115 KB vs ~320 KB) to save Agenbot tokens;
  `?examples=true` returns the full document, identical to `openapi.yaml`.
- **D35 — Endpoints added to the spec's list** (needed by the UI): `GET /api/auth/session` (which screen to show),
  `POST /api/auth/pin` (change PIN), `POST /api/auth/recovery-codes` (regenerate from Ajustes, PIN-confirmed),
  `DELETE /api/auth/passkey` (disable fingerprint), `GET /api/webhook/status`, `GET /api/export`. Device
  rename/revoke use `/api/auth/devices/{id}`.
- **D36 — `PUT /days/{date}` returns `{ result: created|replaced|proposed, day, proposal }`** with 201 / 200 / 202.
  It is **agent-only** (403 for me; I edit through the granular endpoints).
- **D37 — Draft replace uses the same merge as accepting a proposal** (match calendar blocks by `externalId`,
  agent blocks by `id`; my tracking fields survive). It is just applied immediately.
- **D38 — Tasks inside `PUT`.** Optional `tasks[]` syncs agent-origin tasks for that date (match by `id`, then
  `kind`+`title`; unmatched ones deleted unless done; mine untouched). See Q6.
- **D39 — User-created blocks** get `userOverrides` = all schedule fields: the agent can only set their tracking
  fields while pending.
- **D40 — "Me atrasé" (`shift`)** moves pending, unlocked `agent|user` blocks of the chosen option starting at or after
  `fromTime`, `sleep` included (Q8); never calendar blocks. ±240 min. Blocks may pass midnight (D54), so in practice it
  never fails; 422 `shift_out_of_range` only if a start would leave 00:00–29:59. Shifts by me add `start`/`end` to
  `userOverrides`; by the agent they don't. Every shift is one `shift` ChangeLog entry (`{ fromTime, minutes,
  blocks: [{ id, from, to }] }`) and one `shift` webhook change.
- **D41 — `choose`** allowed in `draft` and `chosen` (switch), not in `edited`/`closed`. Both actors may call it.
- **D42 — A new proposal does not bump `Day.version`** (the day did not change); the client learns about it from the push
  and `pendingProposal` in `GET /days/{date}`.
- **D43 — ETag** is the strong `"<version>"`; `If-Match` also accepts `W/"<version>"`. Body `version` is the alternative.
- **D44 — `by-external` has no version check**: the agent always writes the latest calendar state, to every copy.
- **D45 — Proposal diff** is computed against my chosen option: `added`, `removed`, `moved`, `changed`,
  `keptRemovedFromCalendar`, `preservedOverrides` (agent changes that will be ignored), `dayFields`.
- **D46 — Problem details** carry extra members: `current` (on conflicts), `retryAfterSeconds`, `remainingAttempts`.
  PIN lockout answers **429 `locked_out`** with `Retry-After`.
- **D47 — Weeks are Monday–Sunday (ART)** for weekly habits, `weeklyGym`, metrics and streaks.
- **D48 — Metric definitions.** Completion = done / total blocks of the chosen option (option A if never chosen).
  Show-up rate = (with outcome − no_show − rescheduled) / (with outcome − rescheduled). Close rate = closed_won /
  showed up. Gym and reading counts come from the habits linked to block types `gym` / `reading` (D29).
- **D49 — Skipped patterns** (`/agent/context`): agent blocks with the same type and start hour, skipped ≥ 3 times
  and in ≥ 50 % of occurrences over the last 14 days.
- **D50 — Agent vs my tasks.** The agent cannot edit or delete tasks I created, except marking them done while not done.
- **D51 — Habit routes accept id or slug** (`/api/habits/gym/logs`).
- **D52 — `DELETE /api/push/subscribe`** takes `{ endpoint }` in the body.
- **D53 — Re-plans on chosen days** may send only the chosen option; the body must include its label and omitted options
  are kept unchanged.

## Late times and sleep (after STOP 2 feedback)

- **D54 — Block times go up to 29:59.** `24:00`–`29:59` = after midnight, on the block's day (GTFS-style), shown as
  `00:15 (+1)`. Sorting stays lexicographic. `end < start` still means "ends the next day" (`23:30`→`07:00`).
  New contract type `BlockTime`; DB CHECKs updated (`drizzle/0003`). Plain `LocalTime` (00:00–23:59) remains for
  non-block times.
- **D55 — `sleep_log`: actual sleep per night.** `date` = the night starting that day; `bedAt` / `wokeAt` timestamps,
  each with its own source (`agent | user`) so ownership is per half: the agent may only fill an empty half.
  Derived in the API: `durationMinutes`, `plannedStart/End` (the `sleep` block of the chosen option),
  `bedDelayMinutes`. CHECK: wake after bed, < 20 h.
- **D56 — Quick buttons** `POST /api/sleep/events { type: bed | wake, at? }` ("Me voy a dormir" / "Me levanté");
  the night is the previous day when the time is before 12:00. `bed` marks that day's pending `sleep` block done
  (`statusAt` = bedAt). Manual load/correction: `PUT /api/sleep/{date}`, allowed on closed days. The agent can log
  it too ("anoche me dormí 00:20").
- **D57 — Morning reminder.** At `SLEEP_REMINDER_TIME` (default 10:00 ART), if last night has no `bedAt` or no `wokeAt`,
  push "¿A qué hora te dormiste / levantaste?"; per device toggle `push_subscription.sleep_reminders`. "Hoy" shows
  the same card until it is filled (`Day.sleep.previousNight`).
- **D58 — Where sleep shows up.** `Day.sleep { night, previousNight }`, `AgentContext.lastNightSleep`, `Metrics.sleep`
  (nights logged, avg duration, avg bed/wake time, avg delay vs plan), webhook `sleep_log` changes.
- **D59 — Background jobs run in-process** (one container): a loop started from Next's `instrumentation.ts` every 30 s
  delivers the webhook outbox, the 10-min call reminders and the sleep reminder. Only close-day is an external
  Coolify scheduled task, as specified.

## Design: Sistema Calma (see docs/design.md)

- **D60 — "Armar mi día"**: `POST /api/days/{date}` (user) creates the day with one empty option `A` ("Mi día"),
  already `chosen`. A later agent `PUT` becomes a proposal. 409 if the day exists.
- **D61 — Per-block reminder** `block.remind` ("Avisarme 10 min antes"), mine, default true for calls. A push is sent
  when the block is pending, `remind` is on and the device's reminder toggle is on (`drizzle/0004`).
- **D62 — Metrics `range=year`** for the design's Semana · Mes · Año control.
- **D63 — Icons as an SVG sprite** (`pnpm icons`, checked in CI) instead of the Material Symbols font.
- **D64 — Theme**: system preference with dark as the base; per-device override stored client-side (localStorage).
- **D65 — Morning-only sleep reminder** (confirmed): no bedtime nag.
